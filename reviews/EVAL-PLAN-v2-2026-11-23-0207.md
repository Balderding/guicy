# PLAN-v2 (draft 5): outside evaluation

2026-11-23 02:07. Evaluator for Master Control. I only read files and ran git log. Nothing was
built, run, edited or deleted. I read: reviews/PLAN-v2-ruling.md, critic r1-r5, responses r1-r4,
PLAN-v2.md, PLAN.md, PLAN-tiling.md, BENCH.md, bench/stress.md, bench/compare.md,
research/gpu.md, guicy.h (at 6533e6c), and the three apps' sources where the plan's claims touch
them.

## Verdict: GO WITH CHANGES

The F1 and H1 steps are right and should start now. The plan honours every binding user decision
(the checks are below). But it spends most of its effort, early on, on things the three apps will
never use:
- G1 at position 3, which the plan's own every-case rule will almost certainly keep from being the
  default;
- the zoom preview;
- Present1 dirty rects;
- T2-T6, W4-W6.

It also has no migration or rollback plan for the app ports, and those ports are where the real
value is: 7-26 ms per mouse move today, about 0.1 ms with GUICy.

## Numbered changes

1. **Write the binding r5 P2s into PLAN-v2.md (draft 6) before F1.** The plan text still
   contradicts the ruling:
   - D1 l.308-312 keeps em floats right into the layout, and l.270 rounds "each rect edge on its
     own". The ruling instead says the theme is resolved to whole pixels once and the layout keeps
     its integer maths. The integer sites are, for example, guicy.h:2104 and :2108
     (`(int)((float)(r.w - 6) * t->ratio)`).
   - The preview proof is still in G1 (l.241-244), and G1 still names "a move between monitors"
     (l.195).
   - The example `row_h = 24 / 15 em` (l.311) is wrong: today's `row_h` is 28 (guicy.h:532-533).

   A build session working from the plan alone would build the rejected version.

2. **New order:**
   ```
   F1 -> H1 -> G0 (spike) -> D1 -> X1 (fallback glyphs first) -> L1
      -> A1 pilot port (with the user's OK) -> A2, A3
      -> G1 (opt-in, only if G0 allows)
      -> G2, T1, P1 (default parts)
      -> T2-T6, W1-W6 only on the user's ask
   ```
   - The apps' needs are covered by the v1 widgets (PLAN.md l.17-19: about 70 Nuklear calls plus
     their helpers) plus scaling and text.
   - Porting early tests the API on real code before six widget steps are designed blind.
   - L1 stays before the ports because it is a user ask and part of the core. It is not needed to
     port.

3. **Add G0, a 1-day GPU feasibility spike, before G1.** Build the smallest D3D11 path: device,
   flip swap chain, one Map/Draw/Present of about 500 instances. Measure its fixed CPU cost per
   frame against the CPU path's typing and caret frame, 0.059-0.062 ms with 1 tile
   (stress.md §1).
   - The GPU path still pays the same tile hash pass (l.174-175) plus Map, Draw and Present1.
     A D3D11 Present alone usually costs tens to hundreds of µs.
   - So under "every case, ties lose" the GPU will almost certainly lose caret and typing, and
     the CPU stays the default.
   - If G0 shows that, tell the user. The full G1 then becomes opt-in work (`gy_desc.render`),
     built after the ports, and visible race A is never needed. G1 as planned is the biggest step
     (shader parity, pixel-class mask, WARP, child window, device loss, race harness), and its
     main output would be a default that doesn't change.

4. **Drop the zoom preview, or keep it only for a measured slow re-layout.** Tell the user
   honestly why:
   - With the two-pass rule (ruling, P2 #3) the preview is presented and then the crisp frame on
     the next pass. With vsync that shows the crisp frame **one refresh later** than drawing it
     straight away.
   - D1's crisp scale-change frame has a budget of 10 ms or less (l.359), which is under one
     60 Hz refresh. So the preview only adds a blurred frame.
   - It also costs a CopyResource on every drawn frame and about 14.7 MB of VRAM at 1440p
     (critic r5, P2-3), against the "light GPU load" rule.
   - The user's words were "*Or* use the GPU to scale", an alternative, not a requirement.

5. **Simpler swap chain:** use `FLIP_DISCARD` with `Present(1,0)`, and move `Present1` dirty rects
   to "later".
   - research/gpu.md:26 rates dirty rects "small wins on a 4090-class GPU; optional, phase 2".
   - This removes the full-present rule and its DXGI-stub test (l.175-177, 245-247), with no loss
     on this PC.
   - Keep the occlusion rules (l.178-181): they are right, and compare.md note 1 shows how ImGui
     got them wrong on a hidden desktop.

6. **Device loss and the GPU child window, made exact:**
   - Treat `DXGI_ERROR_DEVICE_REMOVED`/`RESET` from **every** call (Map, ResizeBuffers,
     CreateTexture2D, Present), not only Present1 (l.188-189).
   - On the retry, destroy the child window and make a new one, instead of reusing a window
     that a flip-model chain was bound to (ClearState plus Flush before release).
   - "The child is made only when the first GPU frame is ready" (l.186-187) can't be done as
     written, because a swap chain needs the child window first. State the mechanism: a visible
     child with a NULL background brush over the parent's last BitBlt, and no `WS_CLIPCHILDREN`
     on the parent until the first present returns. Prove it with a windowed readback test.

7. **Race statistics:**
   - A median of 3 on a shared PC (l.207) is too few to define "a tie is inside the spread".
     The stress runs themselves note other sessions and a fork failure (stress.md, Method).
   - Use `QueryThreadCycleTime` for the CPU side (W6 already does, l.580), take 9 or more runs,
     and log the other GPU and CPU load.
   - A case whose winner flips between two runs counts as a CPU win.

8. **Test flakiness:**
   - Make functional tests count-based: drawn frames, presents, dirty tiles, wake-ups. Report the
     ms budgets beside them, but don't let them fail the suite.
   - "Idle under 20 ms CPU per 60 s" is one 15.6 ms tick, so a single extra tick fails it.
     stress.md already shows a 46.9 ms "noise" miss. The pass rule should be "0 frames drawn and
     0 presents over 60 s".
   - Run the 60 s idle runs only at steps that touch the loop, as l.87-88 says, not every step.

9. **Monitor handling in D1 (l.274-282):**
   - On `WM_DPICHANGED`, apply the `lParam` rect at once with SetWindowPos. That is the documented
     per-monitor v2 contract. Defer only the same-DPI resolution-term switch to `WM_EXITSIZEMOVE`.
   - On the user's two monitors neither case fires: both are 96 DPI with a 1440 px short side,
     so both get 125 %. Keep this code minimal and stub-tested only.

10. **Pixel-snap thin canvas lines.**
    - Line endpoints stay as float bits (l.326). At 125 % a 1-DIP horizontal or vertical line at
      a .25 offset blurs over 2 px, which breaks "a crisp 1 px border at 125 %" for canvas
      drawing.
    - Snap axis-aligned line centres to pixel centres. Today's box rule, `max(1, floor(w*f+0.5))`
      with each edge rounded (l.270-273), is otherwise correct: 1 px at 125 %, 2 px at 150 %.

11. **Goldens churn:**
    - Make the structural checks instance-list checks with the synthetic font (l.335-340). They
      survive font, theme and ClearType changes.
    - Keep real-font PNG goldens to a small look set per step.
    - Add **120 DPI / 125 %**, the user's real factor, to D1's 96/144/192 set (l.351).
    - A theme or scale change should re-baseline one look set, not three per widget.

12. **Size budget (120 / 140 KB):**
    - Today the core is 86 KB in (i) (BENCH.md:152). The estimate after P1 is about 118 KB
      (l.620-621), which leaves 2 KB.
    - X1's "+3 KB fallback" is low: DirectWrite font fallback in C means implementing
      `IDWriteTextAnalysisSource` by hand. Plan for 5-8 KB.
    - Count `.pdata`/`.xdata` in (ii).
    - Reverse the cut order in l.636-640. CJK file names showing boxes is a real loss for
      pixelhunter, which pulls from any country. So the DWrite fallback and IME are the **last**
      to go, after the first-letter jump, the "Locked" text, and moving G2's arrangements beyond
      side-by-side and tabbed into `GUICY_TILING_FULL`.
    - Still about half of Nuklear's 249-251 KB (BENCH.md:43-45), so the claim holds.

13. **Defer until after the ports, and only on the user's ask:** T2-T6, W5, W6, P1's
    `TILING_FULL` extras, and W4's file dialogs.
    - The apps already have their own dialogs: pixelhunter.c:243 and :271 (`SHBrowseForFolderA`),
      voxup src/pick.c:3056 and :3067 (`SHBrowseForFolderW`, `GetOpenFileNameA`).
    - These steps are the user's goals ("every widget type", tiling WM), not gold-plating in
      themselves, but no app needs them. W1 lists and W2 menus are the likeliest to be needed.
      Check that against the port inventory.

14. **Add an A1-A3 migration section:**
    - (a) A per-app map of the Nuklear calls and the nk_ext helpers to `gy_` calls, with the gaps
      named.
    - (b) bbb_kit: its GDI+ image path and `gy_attach` (bbb_kit.c:1897-1924; the app is already
      per-monitor v2 at :1923, as voxup is at pick.c:3115).
    - (c) Keep the apps' WCAG 4.5:1 contrast self-tests working (voxup pick.c:2189-2214;
      bbb_kit.c:533 and :2045-2048). That needs a GUICy test hook listing every drawn text's
      rect, foreground and background.
    - (d) The ini and layout migration.
    - (e) A before/after sheet: today's 100 % Nuklear picture beside GUICy at 100 % and at
      125 %, with the original shown beside, the user's standing rule.
    - (f) **Rollback:** Nuklear stays in each app behind a build switch until the user signs off
      and one release has shipped. The single-exe rule holds either way.

15. **Add to the core:**
    - Tab and Shift+Tab focus traversal with Enter or Space to activate. Today focus comes only
      from a click (guicy.h:1624, :2823). It is about 1 KB and fits "fewer clicks".
    - High-contrast mode (`SPI_GETHIGHCONTRAST`, then a theme in system colours, about 0.5 KB).
    - Name UI Automation and screen readers as a known gap: fine for three personal tools, but
      say it. IME is already in X1 and is fine.

## Correctness spot-checks

- **The hover and redraw misses and their cause: confirmed.** In `gy__draw_box_cpu`
  (guicy.h:2637-2665), every pixel of the `band = max(radius, border) + 1` top and bottom rows,
  across the whole width, runs `gy__box_px` (:2660). That is two `gy__box_cov` calls with a sqrt
  (:2611-2620), plus a per-channel loop (:2630). The middle rows blend with `k_row` even where
  they are opaque (:2658). That matches stress.md §7: 29.6 µs per box, 63 times a plain rect.
  F1's corner cache, spans and stosd inside are the right fix. The focus-move cause is also
  confirmed: the focus colour is the border of the panel's full box (guicy.h:2321). So is the
  3-layer walk (:2749-2750 and :2763-2765).
- **Swap chain and occlusion:** the rules in l.173-181 are sound. A full redraw on every changed
  frame keeps `FLIP_SEQUENTIAL` dirty rects valid with 2 buffers (research/gpu.md:423-425), but
  see change 5. The child window plus `HTTRANSPARENT` design is sound (same thread). Its real
  input is unproven until visible check B, and the plan says so (l.236-240). Gaps are in
  change 6.
- **The race:** timing from input to the return of Present, the OCCLUDED counts and the
  present-call rule (l.202-224) correctly stop the hidden desktop from faking a GPU win
  (compare.md notes 1-2). The weakness is the statistics (change 7). The prediction that the GPU
  loses the small-frame cases is in change 3.
- **The scaling formula:** correct for every stub in l.352-354. A 1-DIP border becomes exactly
  1 px at 125 %. The 0.75 floor is 1.25 × 0.75 = 0.9375, about 94 % (l.301-302). The resolved
  whole-pixel theme from change 1 is needed for even gaps: gap 6 DIP is 7.5 px, which rounds to
  8 once, instead of alternating 7 and 8.
- **The final crisp frame within 1 frame:** the CPU path meets it trivially (l.359-360). On the
  GPU path the ruling's two-pass rule meets "within 1 frame" in pass count, but it is
  1 refresh later on screen than having no preview (change 4).

## Risks

- **Size:** likely to break the 120 KB at D1 or X1 (critic r5 P3-6 agrees). Change 12 makes the
  trigger cut the right things.
- **Goldens churn:** D1 multiplies every later step's goldens by 3 DPIs. Change 11.
- **The look of the ports:** at 125 % everything is 25 % bigger than today. A 1540-DIP window is
  1925 px, wider than the portrait monitor's 1440 px, so it is capped (l.318-319, 358) and the
  too-small zoom may start there. That is the user's choice, but the before/after sheet
  (change 14e) has to show it.
- **Flakiness:** ms-based pass rules on a shared PC, and the hidden desktop hiding presentation.
  Changes 7 and 8.

## Does the plan stay within the three apps' needs?

Only F1, H1, D1, X1 (fallback glyphs), the v1 widgets, `gy_split`/`gy_dock`-level layout, and
possibly W1/W2 serve the apps. The rest (G1 as the default contender, G2-T6, W3-W6, the preview)
serves the user's library-wide goals. That is legitimate, but it should come after the ports and
be sized against what the ports show.
